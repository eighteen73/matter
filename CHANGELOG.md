# Changelog

## 1.0.0

A rework that moves design decisions out of the editor and into the theme. Not compatible with 0.x content; keep existing sites on 0.x.

### Added

- **Sections:** layout blocks declared in `block.json` (`supports.matter.slots`), with locked `matter/slot` content areas, a shared editor, a default renderer and `Matter\slots()` for custom `render.php`. Whole-block links (`supports.matter.link`), e.g. for cards, replace pulsar-extensions' group link.
  - Slots are matched by name, so they can be added, reordered or removed in `block.json`; a renamed slot lists its old names (`previously`). Content in a slot that's no longer declared isn't output, and the editor keeps it, marked, for the client to move or remove. The list view names a section after its first heading (a name the client gives it wins), and the list view and breadcrumbs name a slot in sentence case (`media-end` is "Media end"), with its own icon.
  - A section's variants are block styles (`styles` in `block.json`); one in its default variant gets that variant's class (`is-style-default`), on the front end and in the editor.
  - Sections are previewed in the inserter from their slots' templates (placeholders as text, a grey picture for images), unless they declare an `example`. So are modals, drawers and collapsibles (shown open); Matter's other blocks have sample content, and posts, products and terms displays preview three items.
  - Lock a slot with `templateLock: "all"` or `"insert"`, not `"contentOnly"`, which hides the blocks' settings (an image's focal point) behind "Edit pattern".
  - An empty slot is marked `is-empty` (on the front end, one that renders nothing; in the editor, one with no blocks). In the editor, a section's inner wrapper isn't positioned, as on the front end; the README lists what else the editor adds.
  - A slot's `alignments` are offered to the blocks in it (e.g. wide and full, for a carousel wider than the text around it). Carousels, galleries, tabs and accordions can be aligned wide or full.
- **Colour schemes:** `supports.matter.scheme`, a swatch control (each named under its swatch), and CSS generated from the theme's `custom.scheme`.
- **Variants:** theme-defined block presets via `matter_variants`, shown as block styles.
- **Menus:** Appearance › Menus rendered by `Matter\menu()`.
  - Dropdown, accordion and drill-down types, switchable per breakpoint without JavaScript.
  - Megamenus built from menu structure, with optional theme panels.
- **Panels:** `Matter\panel()` / `panel_toggle()`, off-canvas below a breakpoint and inline above.
- **Archives:** content above and below post type, taxonomy, search and 404 lists, edited like pages (Appearance › Archives). `matter/archive-content` wraps a template's list; `matter/archive-loop` places it, with variants and a live preview. Terms use their taxonomy's entry, or a parent's or the post type's when that entry is set to cascade (off by default); the newest published entry wins, so new versions can be scheduled. The `matter/archive` bindings source gives the archive's title, description, count and image; a bound block's sidebar says where its text is edited. Customising an archive starts an unsaved draft.
- **Site settings:** config-driven fields (a `url` field adds `https://` to an address typed without it), a React settings page (Appearance › Site details), `Matter\setting()` and the `matter/setting` bindings source.
- **Extensions:** button icon (`matterIcon` on `core/button`; icon registry, chosen from a core-style icon library; `matter_icon_collections`) and focal point (core's own `focalPoint` on image blocks, offered on every image, and featured images); wide and full-width images get `sizes` from their alignment, so they aren't downloaded at the chosen size and stretched.
- Theme-owned breakpoints (`matter_breakpoints`).
- **Loop items:** `matter/loop-item` shows the theme's pattern for an item (`{namespace}/loop-item-{post_type}`, else `{namespace}/loop-item`; `matter_loop_item_pattern`) in every loop and carousel, previewed in the editor as on the front end. Carousels, accordions and tabs of posts can have their own (`loop-item-{post_type}-accordion`, `loop-item-accordion`…), in a template-hierarchy order. A variant can have its own too (`loop-item-carousel-{variant}` before `loop-item-carousel`); the filters are given the variant.
- **Term loop items and terms carousels:** in a Terms Query's term template, `matter/loop-item` shows the theme's pattern for the term (`{namespace}/loop-item-term-{taxonomy}`, else `{namespace}/loop-item-term`; in a carousel the `-carousel` ones first; `matter_loop_item_term_pattern`) with the term's `termId` and `taxonomy` context, else a link to the term, previewed in the editor through `matter/v1/loop-items/terms`. A Terms Query can be shown as a carousel (`matterDisplay`), as "Terms carousel" in the inserter and the carousel's picker, and is allowed wherever `matter/carousel` is.
- **Theme contract:** the README lists what themes and saved content depend on, which changes only in a major version.
- **Theme template parts:** `matter/template-part` renders a PHP file from the theme's `template-parts/` folder in block templates (from Pulsar's `pulsar/template-part`). Its editor preview includes the styles the part enqueues, such as menus and panels.
- **Allowed blocks:** the theme's list (`matter_allowed_blocks`, with `namespace/*` wildcards) is enforced in the post editor. A block a section's slot allows that isn't on the list is offered only in those sections.
- **Theme icons:** the theme's `assets/svg/icons/` SVGs are registered as an icon collection (`matter_theme_icons`).
- **Theme namespace:** `matter_theme_namespace` (and `Matter\theme_namespaces()`) names the prefix of the theme's loop item patterns and its icon collection, so they don't depend on the theme's folder name (default: the folder, then its parent's).
- **JavaScript API:** `matter.carousel()`, `matter.tabs()`, `matter.accordion()`, `matter.gallery()`, `matter.overlay()` and `matter.panel()` return instances with methods and read-only state; `matter.ready()` waits for a block; every block dispatches `matter-{block}-*` events. The block stores take a target (ID or element) too. A small stub in the page's head defines `window.matter` before any module loads.
- **Empty accordion items and tabs** (whose content renders nothing to show, e.g. a product's specifications when it has none) aren't output.
- **Stable IDs for links:** tabs, accordions and posts displays get an ID of their own when added (`matterId`; an HTML anchor replaces it), and items in posts tabs and accordions are named after their post (`#{id}-post-{postId}`). Links to an item open it and anything it's nested in, also on `#hash` changes.
- **Integrations:** what Matter does with WooCommerce and Gravity Forms lives in integrations (`Integrations\WooCommerce`, `Integrations\GravityForms`), booted on `plugins_loaded` only when the plugin is active; Matter's own code names no other plugin. They add through filters a project can use too: `matter_integrations`, `matter_query_blocks`, `matter_query_loops`, `matter_query_display_post_types`, `matter_archive_post_type_title`, `matter_archive_term_image_id` and `matter_hidden_blocks`; in the editor, `matter.queryDisplay.carouselTemplate`, `matter.queryDisplay.displayAttributes` and `matter.carousel.queryOptions`. WooCommerce's editor code (the Products carousel) is its own script, loaded only with WooCommerce.
- **Filters:** `matter/filters`, `matter/filter`, `matter/filters-toggle`, `matter/active-filters` and `matter/results-count`, replacing FacetWP. Filters go inside a Query Loop (or a Product Collection, with WooCommerce): a sidebar that's a drawer below a breakpoint, options with counts, chips, a results count. The URL is the state (`filter_{taxonomy}`, and WooCommerce's own parameters for products), so it works without JavaScript too; with it, the `matter/filters` store navigates with the Interactivity router, or a registered results provider. Sources: any public taxonomy, and with WooCommerce product categories, tags, brands, attributes, price, stock and rating. `matter_filter_sources`, `matter_filterable_query_blocks`, `matter_pre_filter_counts`, `matter_filter_swatch`.
- **Live blocks:** blocks a plugin declares live (`matter_live_blocks`: a price that depends on the customer, a stock level) become placeholders in loop items, filled in the browser, rendered for the visitor at that moment, from `GET matter/v1/live` (script module `matter/live`: `fill()`, `prefetch()`). Placeholders are made for search index cards (`Live::with_placeholders()`) and, if a site turns it on, on pages (`matter_live_placeholders`). Guests' answers are cacheable until the next scheduled change (`matter_live_expires`, at most five minutes), versioned by `matter_live_version`; logged-in visitors' are private, and one without a REST nonce is given one.
- **Prerendered loop items:** `LoopItems\Prerendered::render()` returns an item's loop item, rendered ahead of time so it can be stored and shown somewhere else, such as a search index: rendered as a guest, with live blocks as placeholders, its post classes, the Interactivity data its blocks add and a version (`Prerendered::version()`) that says when it's stale. Hooks: `matter_prerendered_loop_item`, `matter_prerendered_loop_item_version`, `matter_prerender_loop_item_start` and `matter_prerender_loop_item_end`. With WooCommerce, product loop items are rendered without the shopper's cart.
- **Stars and "& up":** a filter for a source with ordered values (ratings, `ordered()`) can show them as `stars`, and with `atLeast` each option includes those above it ("4 & up": one choice, a summed count, one chip; `filter_rating=4,5` in the URL, so nothing else changes).
- **WooCommerce swatches:** attributes' colour and image swatches (WooCommerce 10.9's visual attributes) are their options' swatches, and their filters show swatches at first.
- **Filter parameters follow one convention:** `filter_{name}` (comma-separated values) with `filter_{name}_match=all` for a choice, and `filter_{name}_min` and `_max` for a range, with short names: `filter_category`, `filter_tag`, `filter_brand`, `filter_color`, `filter_price_min`, `filter_stock`, `filter_rating`. A source applies only to queries for its own post types, so a post's and a product's category share `category` (`matter_filter_param_name` renames one). WooCommerce's sources translate theirs into WooCommerce's own parameters as the request starts (`Filters\QueryParams`).
- **Filters with number values** (ratings) name their chips by the right option: their labels were renumbered when merged, so "4" read "Rated 1 out of 5".
- **Range chips in the browser:** a range source can word its chip for the browser (`range_labels()`: "From %s", "Up to %s", "%1$s – %2$s" and how to write an amount). The listing's state carries it, so a provider's results show "Up to £17" as the server does. WooCommerce's price source has one.
- **Live blocks are keyed** (`data-wp-key`), so when the router renders a server page where a placeholder was filled, the placeholder is replaced rather than having the block added beside what was filled.
- **Prices of their own:** with WooCommerce, when a pricing plugin says the shopper has prices of their own (`matter_own_prices`), price filters and price sorting use their prices (`matter_product_prices`). The listing's products are priced for them, filtered and sorted, and the query is limited to them (`post__in`). The browser is told (`ownPrices`), so a results provider leaves those clicks to the server.
- **Results providers:** what a provider needs from the server and the page. `matter_filters_listing` fires once a listing's query block has rendered, with its options, `base_query_vars()` (its query without filters) and `page_param()`. `matter_filters_base_query_vars` and `matter_filters_page_param` filter those. `resultsState()` in `matter/filters` words a provider's results as the server does, and `Live::expect()` loads the live module for placeholders a page didn't render.
- **Filters in templates:** a filterable query block inside another block (Pulsar's archive templates) now navigates without a page load. WordPress builds a nested block before filtering its data, so `enhancedPagination` was never seen, and every filter click reloaded the page.
- **Panels:** `Panel::render()` and `Trigger::button()` take `process` (false in a block's render, whose outermost interactive block processes the directives) and the button takes `content`.
- **Loop items** support client navigation, so a Query Loop or Product Collection holding them can navigate without a page load.
- **Query lists:** every loop template's list (a Query Loop's, a Terms Query's, a Product Collection's) has the class `matter-query-list`, on the front end and in the editor; carousels and accordions of a query find their items by it.
- **Tests:** PHPUnit (with contract markup snapshots), JavaScript unit tests and a Playwright and axe browser suite, run in CI against wp-env, and weekly against WordPress nightly and the latest WooCommerce.

### Changed

- **Accordion:** two blocks (accordion, item), with FAQ schema output inline. An accordion of posts is a Query Loop shown as one ("Posts accordion"), its content the theme's `loop-item-accordion` pattern (or a post type's own).
- **Posts displays in the inserter:** found by the site's post type names as well as their own keywords ("faq" finds Posts accordion), and Posts accordions and tabs list up to 100 items (core's most) rather than 10, since nothing pages through them.
- **Tabs:** two blocks (tabs, tab). Tabs of posts are a Query Loop shown as tabs ("Posts tabs"). The tab list is built on the server. Horizontal or vertical, optional tab icons (chosen on the block toolbar), tabs removed with Backspace in an empty name or "Delete tab", and optionally a dropdown on smaller screens (showing tab icons), where the theme sets the breakpoint.
- **Carousel:** one block. Slides are its inner blocks, and behaviour comes from variants. A carousel of posts or products is the Query Loop or Product Collection itself (`matterDisplay`), shown as "Posts carousel" and "Products carousel" with the query's own filters. The theme's slide types (`matter_carousel_slides`) are offered when a carousel is added; one with `within` only in carousels inside those blocks. A carousel that already has a variant (from a section's template, say) keeps it whatever its slides are.
- **Gallery:** grid or carousel layout, with a native `<dialog>` lightbox. Editors choose the columns (from the theme's choices) and an aspect ratio preset; the theme sets the image size. The grid can show the first N images, in whole rows at any width, with a "View all" button. Images are managed in the media library's gallery mode, as in core's Gallery. Captions show behind an info button, over the image or not at all (the theme sets the default), and in the lightbox. Embla is now bundled once.
- **Modal, drawer and collapsible:** single blocks with an optional trigger area and a content area, also opened by any link to `#id`. Modal and drawer use native `<dialog>` and can be made non-closable (e.g. an age gate). Per-post overlays in Query Loops, and grouped modals with previous/next, which keep the backdrop while switching. URL parameters open an overlay even after a dismissal. There's a new `matter/overlay` store. In the editor, the canvas shows only what the front end shows: closed overlays show just their trigger (if any), and an overlay opens as it does on the front end (theme styles, backdrop, transitions, group previous/next) while it's selected. An Overlays sidebar lists and adds modals and drawers, link search suggests overlays by name, and buttons that open one get "Edit modal" (or drawer, collapsible).
- **Dialog exits:** modals, drawers and gallery lightboxes animate out in every browser: a closing dialog stays open with `is-closing` until its transitions finish (CSS alone could only animate the exit where `overlay` can be transitioned, i.e. Chromium).
- **Shared focus trap:** focus-trap is one script module (`matter/focus-trap`) shared by menus and panels, so it loads once and their traps share a stack.
- **CSS:** functional rules at one class (context in `:where()`) plus a minimal default skin entirely in `:where()`, motion and icons included, so one theme class overrides any of it wherever the theme's stylesheet loads (see the README's CSS conventions). Selectors are written out in full, with nesting only for the same element, enforced by stylelint. No custom-property fallback chains and no inline styles from attributes. Block variables are named `--{block}-{setting}` (e.g. `--gallery-gap`, `--carousel-per-view`); colour schemes set 11 roles (`background`, `background-surface`, `background-fill`, `text`, `text-subtle`, `text-heading`, `text-link`, `text-fill`, `border`, `border-strong`, `highlight`) as `--scheme--{role}`.
- **Direction:** one stylesheet per component, with logical properties and `:dir(rtl)`, instead of flipped `-rtl.css` copies, so right-to-left content works on any site. Drawer and panel sides are `start` and `end` (drawer `position`, `.is-position-start`; panel `position`, `.is-from-start`), not left and right.
- **Carousel settings:** `--carousel-per-view` and `--carousel-gap` set slide widths and gaps.
- **Core blocks Matter replaces:** hidden with `supports.inserter` instead of rewriting the allowed-blocks list.
- **Requirements:** WordPress 7.1 and PHP 8.3.
- **Dependencies:** pinned; unused packages removed.

### Removed

- **Navigation:** `matter/navigation` and `matter/navigation-megamenu` blocks, and the megamenu template-part area (replaced by menus).
- **Carousel children:** `carousel-viewport`, `carousel-slide`, `carousel-thumbnails`, `carousel-dots`, `carousel-progress`, `carousel-previous-button`, `carousel-next-button`.
- **Accordion and tab children:** `accordion-heading`, `accordion-panel`, `tab-list`, `tab-button`, `tab-panels`, `tab-panel`.
- **Overlay pieces:** `modal-content`, `drawer-content`, `collapsible-content`, `trigger`, `trigger-hamburger`, `close`, `modal-navigation` (now built into the modal's group option).
- **Per-instance design controls:** colours, spacing, borders, breakpoints, backdrop and size settings.
- **Legacy shared code:** `config/block-styles.json` and the block styles engine, the old overlay and lightbox stores, and the ID/context helpers.

### Visual changes

Changes to the default skin (in `:where()`). From 1.0 the skin changes only in a major version, or to fix a bug or an accessibility failure; see the theme contract in the README.

- The skin is minimal: no radii (modal, dropdown, tooltip, caption and carousel buttons), shadows, font weights (toggles, tabs, labels), decorative borders (accordion items, the tab list, drill-down rows and header, carousel arrows) or opacity effects (thumbnails, menu descriptions).
- Dropdown submenus and the tabs dropdown have a border instead of a shadow; the selected tab is underlined (both orientations) instead of a border on its side.
- Surfaces fall back to the system colours `Canvas` and `CanvasText` without a scheme, and tints (progress and timer tracks, borders) are mixed from the text colour, so they show on dark schemes.
- Icons, dots, progress bars and the panel toggle's bars stay visible in forced colours.
- Carousel dots are sized in `rem` (0.625rem) and spaced with their centres 24px apart; menu toggles, back buttons and links, and overlay close buttons, are at least 24px, for WCAG 2.5.8's target size.
- Reduced motion also stops the transition between grouped modals.
